# Amber — ревью перед альфа-билдами

*Ревью кодовой базы на коммите `77d06c8`, 2026-06-10. Сборка чистая, `go vet` чистый,
полный `go test ./... -count=1` зелёный (в CI гоняется с `-race` — отлично).*

---

## Вердикт в двух абзацах

Это сильный проект. Для одного человека — очень сильный. Архитектура трёхслойная и
честная: модель → storage → индексы → query, границы пакетов осмысленные, в коде много
комментариев уровня «почему», со ссылками на спеки и результаты нагрузочных тестов
(`INDEX_EVICTION_SPEC_v0 §2`, `loadtest_v0 §4`) — это культура, которой нет у большинства
команд. Протокол durability для логов/спанов (WAL seq-watermark, truncate-to-synced-size,
footerless recovery, атомарный meta.json через tmp+fsync+rename) продуман и закрывает
неочевидные crash-окна. Бенчмарки в README с честной методологией и признанием слабых мест —
большой плюс доверия.

Главные риски для альфы не в «полировке», а в нескольких конкретных местах: (1) окно
дублирования записей при краше во время ротации сегмента; (2) движок метрик **не открывается**
после torn write в своём WAL; (3) связка compaction+retention в метриках приводит к тому, что
данные **никогда не удаляются**; (4) нет блокировки каталога данных — два процесса молча
портят базу; (5) float-метрики хранятся как int64×1000 с тихой потерей точности. Всё это
чинится локально, без перестройки архитектуры. Ниже — по приоритетам.

## Что хорошо

### Архитектура и код
- **Слоистость без протечек (в логах/спанах).** `model` → `storage` → `index`/`indexer` →
  `query` → `ingest` → `runtime` → тонкие `amber.go` и `cmd/amber`. Embedded API и standalone
  бинарь честно делят один `runtime.Stack`.
- **Комментарии объясняют решения, а не строки.** Примеры: преамбула к `walMagic`
  (`storage/wal.go:18-23`) объясняет, зачем v2 добавил seq; `segment_manager.go:151-156`
  документирует окно «saveMeta-then-truncate». Это то, что обычно теряется — у вас оно в коде.
- **Durability-протокол логов/спанов.** WAL с CRC и monotonic seq; checkpoint по флашу блока
  с записью `LastSyncedSeq`/`LastSyncedSize`; на старте — truncate сегмента до синхронизированного
  размера + replay хвоста из WAL с фильтром `seq <= syncedSeq`. Дедупликация после краша решена
  правильно (за одним исключением, см. P0-1).
- **Recovery многоуровневое:** footer → footerless scan (`segment.go:417`), meta → rebuild,
  каталог метрик: catalog log → legacy JSON → rebuild из блоков. Битый WAL логов не валит
  процесс, а останавливает replay и считает `CorruptRecords` — правильная политика для лог-стора.
- **Метрики: flush-протокол с маркерами** (`prepared`/`committed` + наличие WAL-записей как
  тай-брейкер, `store.go:361-447`) и атомарная запись блока (tmp+fsync+rename+syncDir) — это
  уровень «взрослых» TSDB.
- **Group commit** в metrics-WAL (`committer.go`, 5ms) и батчевый fsync в логовом WAL
  (`WriteBatchTS` с инкрементальным CRC без аллокаций — видно, что профилировали).

### Query-слой
- Каскад отсечений для логов: sparse index (сегменты по времени) → bitmap/FTS/ribbon/posting →
  block skip по min/max ULID → top-k heap с порогом по сегментам (`executor.go:766-771`).
  Использование того, что ULID лексикографически time-ordered, для block skip — элегантно.
- Reverse scan + cursor-пагинация вместо offset — правильный выбор.
- Кэш результатов с singleflight-дедупликацией inflight-запросов и осознанным решением
  не кэшировать пустые ответы (с комментарием почему).

### Эксплуатация
- Cardinality guard, circuit breaker на консекутивных ошибках, backpressure через
  `ErrQueueFull`, HTTP 202 (честный «принято, не записано»).
- Constant-time сравнение API-ключей с проходом по всем ключам (`helpers.go:70-76`) — мелочь,
  но показательная.
- Selfobs + dogfood-скрейпер собственных метрик в свой же движок — лучший способ найти баги
  метрик-движка.
- S3-tiering: uploader с persisted attempt-counter для backoff через рестарты, reconcile/adopt,
  cold fetch через singleflight. Для альфы — неожиданно зрело.
- Retention с локальным и глобальным tier'ом и причинами эвикции в метриках.

### Процесс
- CI с `-race`, lint, тесты на crash-recovery (`catalog_log_test`, `eviction_boundary_test`,
  cursor integration). Бенчмарки против Loki/ClickHouse/OpenSearch с опубликованной методологией.

## Критично для альфы (P0)

> **Статус (2026-06-10):** все пять P0 исправлены в рабочей копии:
> P0-1 — порядок truncate в `rotate()` + регрессионный тест;
> P0-2 — `wal.RecoverReplay` с обрезкой битого хвоста + тесты на torn write;
> P0-3 — `Compact()` отбрасывает сэмплы старше retention (вариант drop-expired;
> time-bucketed compaction остаётся стратегическим планом);
> P0-4 — `internal/fslock`, лок берётся в `runtime.New` и `store.Open`;
> P0-5 — валидация NaN/±Inf/overflow в engine и OTLP-адаптере, скипы считаются
> в `metrics_ingest_rejected{reason="value_unencodable"}`, модель значений
> задокументирована в README.

### P0-1. Окно дублирования записей при краше в `rotate()`
`storage/segment_manager.go:357-411`. Порядок: seal old (saveMeta) → `createNewSegment()`
(saveMeta с новым unsealed-сегментом, `LastSyncedSeq=0`) → `wal.Truncate()`.

Краш между `createNewSegment` и `Truncate`: при рестарте `replayWAL` находит активным **новый**
сегмент с `LastSyncedSeq=0` и реплеит в него **весь** WAL — все записи, которые уже лежат в
только что запечатанном сегменте. Полный дубль сегмента данных.

**Фикс простой:** перенести `wal.Truncate()` до `createNewSegment()`. Краш между seal и
truncate уже корректно обрабатывается веткой «нет unsealed-сегмента → drop orphan records»
(`segment_manager.go:110-120`).

### P0-2. Движок метрик не открывается после torn write в WAL
`metricsengine/wal/wal.go:170-171` — `Replay` возвращает ошибку при CRC mismatch, и
`store.Open` падает (`engine.go:51-55`). Torn write на краше — это *штатный* сценарий для WAL:
если заголовок записи (длина) долетел, а payload частично — CRC не сойдётся, и база больше не
стартует без ручного вмешательства. То же с «record too large».

Логовый WAL ведёт себя правильно (стоп replay + счётчик + продолжение работы,
`storage/wal.go:297-302`) — у двух WAL в одном проекте **противоположные политики обработки
коррупции**. Унифицируйте: для хвоста WAL — truncate-and-continue (опционально с сохранением
повреждённого хвоста в `*.corrupt` для диагностики).

### P0-3. Compaction метрик делает retention неработающим
- `Store.Compact()` (`store.go:507`) сливает **все** блоки в один.
- `DeleteBefore()` (`store.go:479`) удаляет только блоки целиком по `MaxTime < cutoff`.

С включёнными `CompactionMinBlocks` и `Retention` объединённый блок постоянно поглощает свежие
блоки, его `MaxTime` всегда свежий → retention не срабатывает **никогда** → диск растёт
неограниченно. Это не теоретический кейс, это дефолтный продакшен-режим.

**Фикс:** time-bucketed compaction (окна по 1–2ч, как в Prometheus TSDB) — компактить только
внутри окна; и/или выкидывать сэмплы старше retention в момент компакции. Заодно уйдёт
проблема «Compact читает все блоки в память целиком» (`store.go:519-537`).

### P0-4. Нет блокировки data-каталога
`grep flock` по репо — пусто. Два процесса amber (или два `amber.Open()` на один каталог —
позиционирование «SQLite for observability» прямо это провоцирует) будут параллельно писать
WAL, meta.json и сегменты → тихая коррупция. Нужен `flock` на lock-файл в data dir при
`Open`, с понятной ошибкой «already in use». Пара часов работы, спасает от худшего класса
багрепортов альфы.

### P0-5. Float-метрики: тихая потеря точности и риск overflow
`metricsengine` хранит значения как `int64`; float'ы — через scale, по умолчанию ×1000
(`otlp/adapter.go:53-60`). Последствия:
- gauge `0.0004` → `0`; всё, что мельче 0.001 — исчезает молча;
- значения >9.2e15 — overflow `int64(math.Round(v*1000))` с мусором на выходе;
- `__scale__` попадает в **лейблы** (`adapter.go:85`) — одна метрика с разными scale = разные
  серии, и магический лейбл виден пользователю.

Для альфы минимум: документировать ограничение + валидация на overflow/underflow с метрикой
отбраковки. Стратегически int64+scale как единственная модель для произвольных OTLP-гейджей
не выживет — понадобится либо float64-кодек (Gorilla/XOR), либо честный per-series scale в
метаданных серии, а не в лейблах.

## Важно, но не блокер (P1)

### P1-1. `ensureCatalog` — O(N серий) на каждый append-батч
`store.go:252-255`: на **каждый** `AppendBatch` строится map по всему каталогу заново. При
100k активных серий и push каждые 100мс это миллионы map-вставок в секунду под `s.mu`,
блокирующих и flush, и запросы. Вы уже убили JSON-rewrite-bottleneck (комментарий на
`store.go:302-307`) — это его младший брат. Держите `map[string]uint64` как поле Store и
обновляйте инкрементально (eviction sweep уже знает, что удалять).

### P1-2. Запросы к одному сегменту сериализуются
`reader_cache.go`: на сегмент один `*SegmentReader`, и `acquire` держит `cr.mu` **на весь
скан**. Два конкурентных запроса к одному горячему сегменту выполняются строго по очереди.
Причина — `scanBlock` делает `Seek` на общем `*os.File`. Перейдите на `pread`
(`file.ReadAt(buf, offset)` вместо Seek+Read) — reader станет stateless по позиции, и
один файл-хэндл сможет обслуживать конкурентные сканы без локов. Это и проще, и быстрее.

### P1-3. Кэш результатов обнуляется каждым ingest-батчем
`batcher.go:437-439` — `ClearResultCache()` после каждого батча (по умолчанию каждые ≤100мс).
При любом постоянном потоке записи hit rate кэша ≈ 0, но каждый запрос продолжает платить
sha256 + inflight-bookkeeping. Результаты по **sealed**-сегментам инвалидация ingest'а не
устаревают — инвалидируйте только «хвост» (активный сегмент) или признайте кэш бесполезным
под записью и упростите.

### P1-4. Чтение head метрик = полная копия буфера на каждый запрос
`engine.Snapshot()` → `head.Snapshot()` копирует и сортирует **все** буферизованные серии и
сэмплы под локами на каждый Select/Aggregate/Rate. При большом буфере (а flush по умолчанию
редкий) каждый запрос — O(весь head). Для альфы хватит: сортировать лениво (флаг «отсортировано»
на серию), копировать только серии, прошедшие селектор.

### P1-5. metrics-WAL пишет полный label set каждого сэмпла в JSON
`wal/wal.go:97-99` + `Record{Labels...}`. Каждый сэмпл серии с 10 лейблами тащит ~сотни байт
JSON. У вас уже есть катало́г с series ID и group-commit — пишите в WAL бинарные
`(seriesID, ts, value)` после REGISTER (формат логового WAL можно переиспользовать почти
целиком). Это разом уменьшит WAL на порядок и ускорит replay.

### P1-6. Histogram store: один блок-файл на каждый OTLP-запрос, без компакции
`otlp_metrics.go` («Histogram series from one request are written as one block») +
`histogram/store.go` — компакции нет, retention только удаляет старое целиком, каждый запрос
делает `blockPaths()` (readdir) и читает все файлы. Агент с push раз в 10с — это 8640 файлов
в сутки с одного агента; квантильный запрос за час будет открывать сотни файлов. Нужна хотя бы
простейшая компакция «склеить N мелких блоков», иначе гистограммы не переживут первый
недельный прогон.

### P1-7. Bitmap-индекс не используется для multi-value фильтров
`executor.go:1274-1286`: `buildBitmapConditions` берёт поле только при **ровно одном** значении.
`service=a,b` или `level=ERROR,WARN` — полный скан сегмента, хотя OR roaring-битмапов почти
бесплатен. Это самый дешёвый из крупных перф-выигрышей в query-слое.

### P1-8. `metricsengine` экспортирует внутренности
`metricsengine/metricsengine.go` — ~70 реэкспортов, включая явные детали исполнения:
`AggregateByLabelStepsInBlockWithDirectory`, `SumByLabelInBlock`, `SelectBlockWithDirectory`...
Публичный контракт альфы должен быть `Store + Plan + Execute + Explain` (+ типы). Каждый
экспортированный `*InBlockWithDirectory` — это API, который вы будете обязаны не ломать.
Сейчас сократить дёшево, после альфы — уже поздно.

### P1-9. Durability-семантика embedded API не документирована
`db.Log()` возвращает `nil` после постановки в очередь (10k записей по умолчанию) — до WAL.
`kill -9` теряет очередь+батч. Для HTTP это честно выражено 202-м кодом, но пользователь
embedded-библиотеки, читающий «Write-Ahead Log for crash recovery» в README, ожидает другого.
Минимум — абзац в README/godoc; хорошо бы `db.Flush(ctx)` для барьера и, позже, опциональный
синхронный режим.

## Мелочи (P2)

- **README vs код:** README обещает `segment_max_records` default `1000000`, код —
  `100_000` (`runtime.go:98`). Бейджи CI указывают на `ci.yml`/`lint.yml`, файлы называются
  `ci.yaml`/`lint.yaml`. `index_cache_size` в README назван «Max sealed index readers», а
  реально это ёмкость пяти LRU + reader cache каждый.
- `amber.Open(dir string, opts ...*Options)` — вариадик указателей как opt-pattern читается
  странно; обычный `Open(dir, *Options)` (nil = дефолты) проще. `db.Log(ctx, ...)` игнорирует
  ctx — либо уважать (отмена ожидания очереди), либо убрать из сигнатуры до стабилизации API.
- `QueryTrace(traceID, limit)` применяет limit отдельно к логам и к спанам — стоит
  задокументировать.
- `queryCache.getLog` возвращает копию результата, `getSpan` — общий указатель
  (`executor.go:174-198`): несимметрично, кэшированный `SpanResult` мутируем извне.
- `nextBlockPathWithPrefix` использует `time.Now()` напрямую при инжектируемом `s.clock`.
- Footer сегмента и каталог блока метрик без собственного CRC (payload-блоки прикрыты CRC
  zstd-фрейма, directory метрик имеет CRC — а вот footer логового сегмента только magic).
  Не страшно (есть footerless recovery), но стоит зафиксировать осознанность решения.
- Ошибка `fsync` сейчас просто возвращается наверх, файл продолжает использоваться. После
  неудачного fsync состояние страницы в ядре неопределено (история «fsyncgate» в PostgreSQL);
  безопасная политика — считать WAL/сегмент после fsync-ошибки невалидным (переоткрыть/ротировать
  или fail-stop).
- `Executor.Services()` декодирует каждую запись активного сегмента на каждый вызов —
  дешевле собирать множество сервисов в `ActiveIndex`.
- В `runtime.Stack.Close` метрик-стор закрывается, у histogram-store `Close` нет вовсе —
  пока ему нечего закрывать, но асимметрия станет багом, как только появится фоновая горутина.

## Чего не хватает в тестах

Юнит-покрытие хорошее, но альфа-риски лежат в другом классе сценариев:

1. **Crash-injection.** Симуляция kill в случайной точке протокола (после WAL-write / между
   saveMeta и truncate / посреди flush-маркеров) с проверкой инварианта «нет потерь, нет
   дублей». P0-1 такой тест нашёл бы за минуты. Удобно сделать через интерфейс FS или
   отдельный харнесс с реальным kill -9 дочернего процесса.
2. **Corruption-injection.** Порча случайных байт в WAL/сегменте/футере/каталоге + проверка,
   что база (а) открывается, (б) честно сообщает о потере. Сейчас политика по подсистемам
   разная (см. P0-2) — тест зафиксирует контракт.
3. **Эквивалентность путей запросов.** У метрик 7 execution paths (directory aggregate,
   bucket, summaries, exact...) и property-тест «любой путь даёт тот же результат, что
   наивный full scan» на рандомных данных — самый дешёвый способ ловить расхождения. То же
   для логов: indexed vs полный скан.
4. **Soak с retention+compaction.** Недельный (ускоренный по clock) прогон с включёнными
   retention и compaction — поймал бы P0-3 и P1-6.
5. **Clock skew / event time.** Записи с timestamp из прошлого/будущего против sparse-индекса
   и сортировки в блоках: min/max-диапазоны это переживают, но границы стоит покрыть явно.

## Стратегические заметки (после альфы)

- **Унификация трёх движков.** Сейчас три модели durability: логи/спаны (бинарный WAL+сегменты),
  скалярные метрики (JSON WAL+блоки), гистограммы (без WAL, блок на запрос). Для «одной базы
  на всю observability» стоит свести к одному WAL-формату и одному жизненному циклу
  «WAL → immutable unit → compaction → retention» с тремя кодеками полезной нагрузки. Половина
  P0/P1 выше — следствия этой троичности.
- **Float-кодек для метрик.** int64+scale упрётся в реальность чужих OTLP-данных. Gorilla/XOR
  для float64 — проверенный путь, и он совместим с вашими zone maps/aggregate buckets.
- **Язык запросов.** Решение держать PromQL вне ядра (V0_HANDOFF) — правильное, но альфе нужен
  хотя бы тонкий парсер селекторов в HTTP API, иначе метрики снаружи доступны только как
  rate/quantile/stats по одному лейблу.
- **JSON-сериализация ответов** — ваши же бенчмарки показывают, что 95% latency это encoding.
  Streaming-encoder или sonic/jsoniter снимет ~50мс с p50 и сделает сравнение с конкурентами
  ещё выигрышнее.
